מצביעים · malloc / calloc · כללי free

שקפים 1–23

תחנה 1 · מעקב מצביעים

תרגול · אחרי שקף 7

וריאציה על ההדגמה מהמצגת — הפעם עם השמת מצביע למצביע.

מה יודפס?

int a = 3, b = 8, *p, *q;
p = &a;
q = &b;
*p = *q + 2;
p = q;
*q = *p * 2;
q = &a;
printf("a=%d b=%d *p=%d *q=%d\n", a, b, *p, *q);

‏a=10 b=16 *p=16 *q=10

שורהabp ⟶q ⟶
*p = *q + 2108ab
p = q108bb
*q = *p * 21016bb
q = &a1016ba

נקודת המפתח: אחרי p = q שני המצביעים מצביעים על אותו תא — שינוי דרך אחד נראה דרך השני.

תחנה 2 · Stack מול Heap

העשרה · אחרי שקף 12

איפה בעצם "גר" הזיכרון ש-malloc נותנת לנו? מפת הזיכרון של תהליך — התמונה שהופכת את כללי ה-free להגיוניים.

Stack ⬇ · משתנים מקומיים, פרמטרים
↕  זיכרון פנוי  ↕
Heap ⬆ · malloc / calloc / realloc
Data · משתנים גלובליים וסטטיים
Code · קוד התוכנית
  • Stack: ניהול אוטומטי — משתנה נולד בכניסה לפונקציה ומת ביציאה ממנה. מהיר מאוד, אבל מוגבל בגודל (בד"כ ~1‎–8MB). לכן int big[10000000]; מקומי יפיל את התוכנית (stack overflow).
  • Heap: ניהול ידני — נולד ב-malloc, מת רק ב-free. גדול (מוגבל רק ב-RAM), ושורד מעבר בין פונקציות — זו הסיבה שאובייקט דינאמי שמוקצה בפונקציה נשאר בזיכרון אחרי היציאה ממנה (שקף 25).
  • למה free(a) על מערך סטטי קורס? כי a בכלל לא ב-Heap — מנהל הזיכרון מחפש שם רשומת ניהול שלא קיימת.
  • למה free(ptr+1) קורס? ‏malloc שומרת מטא-נתונים (גודל הבלוק) ממש לפני הכתובת שהיא מחזירה. ‏free חייבת לקבל בדיוק את אותה כתובת כדי למצוא אותם.

באגים בניהול זיכרון הם לא רק "נקודה בציון": מקובל להעריך שכ-70% מפרצות האבטחה החמורות שמיקרוסופט מתקנת מדי שנה נובעות מבאגי זיכרון בשפות כמו C. זו גם הסיבה שנולדו כלים כמו Valgrind ו-AddressSanitizer שמאתרים דליפות וגלישות בזמן ריצה — שווה להריץ על התרגילים שלכם.

תחנה 3 · צָדים את הבאג

תרגול · אחרי שקף 23

בכל אחד משלושת הקטעים מסתתר באג אחד הקשור להקצאה או לשחרור זיכרון. מצאו אותו.

קטע א'

int *p = (int*)malloc(10 * sizeof(int));
for (int i = 0; i <= 10; i++)
    p[i] = i;
free(p);

גלישה מהמערך: הלולאה כותבת ל-p[10] — התא ה-11 במערך של 10. כמו בשקף 23: התוכנית אולי לא תיפול מיד, אבל free עלול לקרוס כי נדרסו נתוני הניהול של הבלוק.

קטע ב'

int *make_arr(int n) {
    int a[100];
    for (int i = 0; i < n; i++)
        a[i] = i * i;
    return a;
}

החזרת כתובת של משתנה מקומי: המערך a חי על ה-Stack (תחנה 2!) ונעלם ביציאה מהפונקציה. המצביע המוחזר מצביע לזיכרון שכבר לא שלנו (dangling pointer). התיקון: הקצאה עם malloc — אובייקט דינאמי שורד יציאה מפונקציה (שקף 25).

קטע ג'

int *p = (int*)malloc(5 * sizeof(int));
p[0] = 7;
p = (int*)malloc(20 * sizeof(int));
/* ... */
free(p);

דליפת זיכרון (memory leak): ההקצאה הראשונה של 5 שלמים אבדה — אף מצביע לא שומר את כתובתה, ואי אפשר לשחרר אותה יותר. התוכנית לא קורסת, אבל הזיכרון "נעלם" עד סוף הריצה.

תחנה 4 · הבאג של realloc

תרגול · אחרי שקף 30

הבאג הכי נפוץ בשימוש ב-realloc — נמצא גם בקוד של מתכנתים מנוסים.

מה הבעיה?

ptr = (int*)realloc(ptr, size * sizeof(int));
if (ptr == NULL)
    printf("Allocation failed\n");

דליפה במקרה כישלון: אם realloc נכשלת היא מחזירה NULL — אבל הבלוק המקורי עדיין מוקצה ותקף! דריסת ptr ב-NULL מאבדת את הכתובת היחידה אליו. הדפוס הנכון:

int *temp = (int*)realloc(ptr, size * sizeof(int));
if (temp) ptr = temp;
else      /* ptr עדיין תקף */ ;

שימו לב: זה בדיוק מה שעושה הפונקציה read_data בשקף 35 עם המשתנה temp — עכשיו ברור למה הוא שם.

תחנה 5 · למה דווקא פי 2?

העשרה · אחרי שקף 34

המצגת מראה ש-2+4+8+16 < 31 העתקות מול 495 בהגדלה של תא-תא. בואו נכליל — ונגלה שכך בנויים גם ה-vector של ++C וה-list של Python.

שאלה: כמה העתקות בסך הכל עבור n איברים?

אם מתחילים מ-2 ומכפילים פי 2 בכל פעם שהמקום נגמר — כמה העתקות של תאים יתבצעו בדרך להכנסת n איברים?

סכום ההעתקות: 2 + 4 + 8 + … + n/2 + n < 2n — כלומר לכל היותר כ-2 העתקות בממוצע לכל איבר, לא משנה כמה n גדול. זה נקרא עלות משוערכת (amortized cost): פעולה בודדת יכולה להיות יקרה, אבל הממוצע לאורך זמן הוא O(1).

בהגדלה של תא אחד בכל פעם, לעומת זאת: 2+3+4+…+n ≈ n²/2 — ריבועי. עבור מיליון איברים: ‏~2 מיליון העתקות מול ‏~500 מיליארד.

בדיוק כך ממומשים std::vector ב-++C (מקדם 2 או 1.5) ו-list ב-Python (מקדם ~1.125) — הרעיון משקף 35 הוא הבסיס למבני הנתונים הדינאמיים בכל השפות המודרניות.

תחנה 6 · חידון sizeof בזק

תרגול · אחרי שקף 43

שישה סיבובים מהירים. הנחה: מערכת 64-ביט טיפוסית (‎int‎ = 4, מצביע = 8).

double d; sizeof(d + 1)
הביטוי d + 1 מקודם ל-double, לכן 8. ‏sizeof לא מריץ את הביטוי — רק בודק את הטיפוס שלו.
char *s = "hello"; sizeof(s)
s הוא מצביע — sizeof של מצביע (8 במערכת 64-ביט), לא אורך המחרוזת!
char s[] = "hello"; sizeof(s)
כאן s הוא מערך אמיתי: ‏5 תווים + ‏'\0' = ‏6. ההבדל בין מערך למצביע — בדיוק כמו בשקף 40.
sizeof('a' + 1)
‏'a' הוא int בשפת C (הערך 97), ולכן גם ‏'a'+1 — התוצאה 4.
int a[10]; int *p = a; sizeof(p)
שוב מצביע ולא מערך — ‏8. לעומת sizeof(a) שהיה מחזיר 40.
int i = 0; sizeof(i++); // מה ערך i אחרי? (כמה שווה i, לא sizeof)
‏i נשאר 0! ‏sizeof הוא אופרטור בזמן קומפילציה — האופרנד לא מחושב בכלל, ולכן ה-++ לא מתבצע. הפתעה קלאסית בראיונות עבודה.

אתגר לסיום (או לבית)

ממשו את התרגיל משקף 31 — מערך של 5 מספרים אקראיים שגדל ל-6 — בשתי גרסאות: אחת עם realloc ואחת עם malloc + העתקה ידנית + free של הישן. הדפיסו את הכתובת שהמערך מקבל בכל גרסה (printf("%p", ptr)) — האם ‏realloc תמיד מעבירה את הבלוק למקום חדש?
